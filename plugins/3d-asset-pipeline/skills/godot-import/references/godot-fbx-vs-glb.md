# Godot FBX Vs GLB

Godot 4 generally prefers GLB for interchange because GLB is the binary form of glTF, and glTF is the most direct modern asset exchange format for Godot. GLB packages mesh data, materials, textures, skeletons, and animations in one file, and its physically based material model maps cleanly to Godot's StandardMaterial3D defaults.

Godot 4 also accepts FBX through its import pipeline. FBX remains common for animated character workflows because many rigging and animation vendors still return FBX as their most complete format. In this pipeline, Meshy rigging and animation output is FBX, so humanoid and quadruped assets currently enter Godot as FBX.

Static props should use GLB whenever possible. Props usually need reliable mesh, texture, and material transfer more than advanced animation data. GLB is compact, predictable, and works well with Godot's default scene importer.

Animated assets currently use FBX because the upstream animation stage returns FBX. This avoids an extra conversion step that could lose animation tracks, skeleton naming, bind poses, or take metadata.

This is a practical pipeline choice, not a claim that FBX is better for Godot. When an upstream service can provide a clean animated GLB with matching skeleton and clip data, GLB should be evaluated as the preferred import format.

## Material Handling

GLB material data usually maps more directly to Godot materials. Albedo, normal, roughness, metallic, and occlusion texture slots are commonly preserved when the source GLB follows glTF PBR conventions.

FBX material handling can vary by exporter. Some FBX files embed texture references, some use sidecar texture paths, and some contain only material slots without usable texture files. When an animated FBX looks untextured in Godot, inspect the imported materials and confirm any external texture paths are present in the project.

Material paths are especially important for generated assets because vendors may return textures beside the model file, embedded in a package, or referenced by paths that do not exist on the user's machine. Stage 5 only copies the selected model file. Later chunks can add texture extraction or material repair when the vendor output requires it.

For review-loop screenshots, the first priority is that the asset imports as a visible PackedScene with stable mesh, skeleton, and animation data. Material polish can be handled as a fix pass when screenshots reveal missing textures or incorrect slots.

## Format Choice

Prefer GLB when:

- The asset is a static prop.
- Material fidelity matters more than animation data.
- The mesh came from Hunyuan or another glTF-native generation service.
- The asset will be instanced directly in Godot without external DCC editing.

Prefer FBX when:

- The asset has a rig generated by the pipeline.
- The asset has animation clips generated by the pipeline.
- The upstream vendor output is already FBX.
- Converting to GLB would risk changing skeleton or animation data.

Use explicit `--source-stage mesh` only when the user wants the static mesh even though later stages exist. Use explicit `--source-stage rigged` when animation is not desired but a skeleton is still needed. Use explicit `--source-stage animated` when the animated FBX exists and should be the canonical engine asset.

Do not convert formats during Stage 5. The import stage should be deterministic and cheap: choose the source file, copy it into the project, emit import metadata, and update the manifest.

## Import Settings

This stage emits:

```ini
materials/location=0
materials/storage=0
```

`materials/location=0` keeps Godot's default material location behavior for scene imports. This is conservative for generated assets because it lets Godot use its normal imported-material workflow instead of forcing extraction or remapping during the copy step.

`materials/storage=0` keeps Godot's default material storage behavior. This avoids creating extra material resources until the project owner decides whether materials should remain embedded, be extracted, or be replaced by project-authored materials.

The generated `.import` file is intentionally small. It provides stable defaults for the review loop while leaving detailed material extraction and cleanup to later project-specific edits.

`animation/import=true` is set for both GLB and FBX. Static props do not need animation tracks, but leaving the option enabled is harmless and keeps one stable import template for every scene asset.

`meshes/ensure_tangents=true` is useful for normal maps and generated PBR materials. It can add import work, but this is acceptable for the Stage 5 flow because the import happens inside the user's Godot project rather than during the cloud generation stages.

`nodes/root_type="Node3D"` keeps the imported root predictable for Godot 4. Review scenes, wrapper scenes, and gameplay scenes can all instance the resulting PackedScene under a standard 3D node.

The `.import` file also includes a stable `uid://...` value. Godot can generate import metadata itself, but a deterministic UID reduces noisy changes when the same slug is imported repeatedly into the same project.

## Auto Import

Godot watches the project filesystem and picks up copied FBX, GLB, and `.import` files the next time the editor opens the project. If a headless workflow needs the import cache updated immediately, run this from the Godot project root:

```bash
godot --headless --import
```

Use the installed Godot executable name for the local environment, such as `godot4` or a full path to the Godot binary.

For CI or scripted checks, run the import command first, then run Godot import from the project root. The Python script does not launch Godot and does not require Godot to be on `PATH`.

If Godot reports missing textures after auto-import, keep the copied model path stable and adjust material extraction or texture placement in a later fix step. Avoid renaming the asset file unless the manifest and wrapper scene are updated at the same time.

## Common Import Symptoms

If a GLB prop appears correctly but an FBX character appears gray, the likely issue is texture reference transfer rather than mesh import failure. Keep the FBX in place and inspect material slots in Godot before changing the pipeline source stage.

If an animated asset imports with no visible clips, confirm the source stage points at the animated FBX and not the rigged FBX. A rigged FBX can contain a skeleton without game-ready animation tracks.

If a character faces the wrong direction, do not rewrite the model during Stage 5. Let the review loop add a scene-level rotation or a wrapper scene fix so the source file remains reproducible.

If scale is wrong, prefer a wrapper scene or review-loop fix over changing import scale immediately. Generated assets often need visual comparison against the review scene before choosing a stable scale.

If Godot regenerates the `.import` file after editor open, compare the resulting options with the Stage 5 defaults. Godot may add cache-specific fields; the source-controlled intent remains the copied asset, deterministic UID, and conservative scene import parameters.

If the project uses a custom asset layout, still start with `assets/characters/<slug>/` for pipeline output. Move or instance the wrapper scene elsewhere after import if the game project has stricter organization rules.

## Future Notes

Unity and Unreal import support is intentionally outside v0.1.0. Do not add Unity or Unreal routing to the Godot import command. Future engine importers should follow the same pattern: validate the project, copy the selected source file, write minimal engine metadata, and update `stages.engine`.

When vendors improve GLB animation export, revisit the default for humanoid and quadruped assets. The long-term target is the format that preserves skeleton, clips, materials, and review-loop reliability with the least conversion.
