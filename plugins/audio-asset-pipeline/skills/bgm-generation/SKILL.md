# Background Music Generation

Produce candidate `.wav` files for one music asset and record them in the asset
manifest, so the post and review stages have something to work on.

Two music backends share this skill: **ACE-Step 1.5** (`generate_acestep.py`) is
the default for everything, and **MiniMax-Music3** (`generate_minimax.py`) is the
vocal specialist. Read "Backend Routing" before running either.

## Quick Start

Locate the installed plugin directory first; `<plugin-root>` below is that
directory, and every script path is relative to it. Keep the working directory
in the workspace that contains `audio-pipeline-output/`. On Windows, use
`py -3` if `python3` is not available.

1. Confirm the environment once per machine:

```bash
python3 "<plugin-root>/scripts/doctor.py" --stack acestep
```

2. Create the manifest if the asset does not have one yet:

```bash
python3 "<plugin-root>/scripts/init_asset.py" boss-battle-theme --type bgm --mode manual \
  --prompt "driving orchestral boss battle theme, taiko drums, brass ostinato, D minor" \
  --duration 60 --bpm 140 --loop
```

3. Generate candidates:

```bash
python3 "<plugin-root>/scripts/backends/generate_acestep.py" boss-battle-theme
```

4. Listen to every file under `audio-pipeline-output/<slug>/generate/`, then
   record the chosen one in `stages.generate.selected` before moving on.

Useful ACE-Step flags: `--model`, `--candidates N`, `--seed N`,
`--negative-prompt`, `--no-loop-hints`, `--out-name-prefix`,
`--base <workspace>`, `--device`. `generate_minimax.py` takes the same set minus
the ACE-Step-only ones (`--model`, `--negative-prompt`, `--no-loop-hints`).

The first real run downloads the ACE-Step model repository (DiT renderer, VAE,
text encoder and the LM planner - roughly 12 GB) into
`~/.claude/audio-pipeline/acestep/checkpoints`. Nothing is written into the
game workspace. Expect that first run to take a long time; the timeout is 90
minutes. If the download does not finish inside it, the run is recorded as
`timeout` - just run it again, the download resumes where it stopped.

For a vocal song on MiniMax-Music3, swap `--stack acestep` for
`--stack minimax`, add `--vocals --lyrics "..."` to `init_asset.py`, and run
`generate_minimax.py` instead. Read "License Notice" and "MiniMax-Music3 Cost"
before doing so - that backend has a product-facing attribution requirement and
a much larger download.

## License Notice

**Audio generated by `generate_minimax.py` carries a licensing obligation.** The
MiniMax-Music3 Community License requires that any commercial product or service
shipping that audio **display "MiniMax-Music3" prominently in its user
interface** (section 3.1), and organizations whose products earn over US$20M a
year must obtain separate written authorization from MiniMax first (section 3.2,
`api@minimax.io`).

In practice: put the credit in the game's credits or legal screen as soon as a
MiniMax candidate is selected, not at ship time. The driver prints the notice
after every successful run and records `params.licenseNotice` on every candidate,
so the manifest carries the obligation forward. **Tell the user about it** when
routing a request to this backend - it is a product requirement, not a footnote.

ACE-Step 1.5 and Stable Audio 3 carry no equivalent UI-attribution clause.

## Backend Routing

| Backend | Use it for |
| --- | --- |
| `generate_acestep.py` (default) | Anything that should sound like a piece of music: themes, battle tracks, loops, and vocal tracks that are still being explored. Structure, tempo and key control live here. 48 kHz, fast (tens of seconds per candidate), reference-audio conditioning. |
| `generate_minimax.py` | Vocal quality specialist: the final take of a song whose singing has to carry the scene - an ending theme, a character's song, a credits ballad. Best-in-class vocals, but **slow** (many minutes of GPU time per candidate) and 44.1 kHz. Requires `vocals: true` with lyrics; no instrumental mode, no reference audio; carries the license notice above. |
| `generate_sa3.py --model medium` | Ambient beds and textures with no musical structure: wind over a ruin, a droning cave hum, a rain layer. Instrumental only, no BPM or key control. |

All three accept `assetType: bgm`. Choose ACE-Step unless the asset is really a
texture (Stable Audio 3) or a finished vocal performance (MiniMax-Music3). See
the `se-generation` skill for Stable Audio 3's model routing, prompt style, and
its own failure table.

Both music backends refuse `assetType: se` outright and point at
`generate_sa3.py`; their minimum length is 10 s, which is longer than most sound
effects.

`generate_minimax.py` also refuses, as a `user_error`, an asset with
`vocals: false` (use ACE-Step - it renders an instrumental in seconds instead of
an hour) and an asset with `referenceAudio` set (the model has no
reference-audio conditioning at all).

## ACE-Step Model Variants

| `--model` | Checkpoint | Steps | When |
| --- | --- | --- | --- |
| `turbo` (default) | `acestep-v15-turbo` | 8 | Everything. Distilled for 8 steps, and it ships inside the main model repository, so it needs no extra download. |
| `sft` | `acestep-v15-sft` | 32 | A quality re-render of an approved idea. Instruction-tuned, not distilled; several times slower and an extra multi-GB download. |
| `base` | `acestep-v15-base` | 32 | Raw base model. Only when `sft` is steering too hard. |

The XL (4B) checkpoints are deliberately not offered: they do not fit a 12 GB
card alongside the LM planner.

Classifier-free guidance is only honoured by `sft` and `base`; `turbo` ignores
it, which is why the driver sets it per model instead of exposing a flag.

ACE-Step pairs the DiT renderer with an LM "planner" that turns the prompt into
structured musical metadata and semantic codes. Which planner is loaded, whether
the DiT is offloaded, and whether INT8 quantization is on are all decided from
the detected VRAM by ACE-Step's own tier table - there is nothing to configure.
If the planner cannot be loaded at all, the backend warns and renders from the
prompt alone, which sounds less structured; the candidate params record which
planner was used (`lmModel`), or `null` when there was none.

## Writing The Prompt (ACE-Step)

The prompt lives in `requirement.prompt`; entries in `requirement.styleTags`
are appended to it automatically. The whole thing must stay under 512
characters.

Name the genre, the instruments, the mood, and the musical facts:

- `driving orchestral boss battle theme, taiko drums, brass ostinato, D minor`
- `calm medieval town theme, lute, recorder, hand percussion, major key`
- `tense synthwave stealth loop, arpeggiated bass, muted kick, minor key`

Guidance that changes the result:

- **Put BPM and time signature in the requirement**, not only the prompt.
  `requirement.bpm` and `requirement.timeSignature` are passed as structured
  metadata and are what makes bar snapping possible. The model honours them.
  BPM must be a whole number in 30-300 and the signature must be 2/4, 3/4, 4/4
  or 6/8; anything else is a `user_error` rather than a silent mis-render.
- **Put the key in the prompt** (`D minor`, `C major`). The manifest has no key
  field, and the prompt is where ACE-Step reads it.
- **Structure tags help**: `intro, main loop, build, no outro` shapes the
  arrangement over the requested duration.
- **The prompt is passed through verbatim.** The LM planner writes the musical
  plan, but it is not allowed to rewrite the caption, so whatever is written
  here is exactly what conditions the model.
- `--negative-prompt` steers the LM planner's guidance only. ACE-Step has no
  negative prompt for the renderer itself, so it is a nudge, not a filter.

## Loops

When `requirement.loop` is true and both `requirement.bpm` and
`requirement.timeSignature` are set, the backend snaps the requested duration to
the nearest whole number of bars and generates that instead. A 60 s request at
140 BPM in 4/4 becomes 35 bars (60.0 s); a 30 s request becomes 18 bars
(30.857 s). The candidate params record `requestedDurationSeconds`,
`barSnappedDurationSeconds`, `bars`, `bpm`, `beatsPerBar` and `timeSignature`.

Both music backends record those fields, but only ACE-Step can act on them.
MiniMax-Music3 takes no structured tempo and treats the duration it is given as a
**ceiling** the language model may stop short of, so there the bar count is an
annotation for the post stage, not something the backend enforced. It also
retries nothing (see "Candidates And Seeds"). Prefer ACE-Step for anything that
has to loop.

Why it matters: a track that ends mid-bar cannot be cut on a downbeat, so its
loop seam either drops musical content or lands off the grid. Fixing the bar
count before generation is the only place this can be solved.

The backend also appends `seamless loop, no intro, no outro, no fade-out,
sustained energy until the final bar` to the prompt of a looping asset, because
the planner writes an intro and a fade-out by default, likes to resolve early,
and none of that survives a loop point. Pass `--no-loop-hints` to turn it off
(for example when the asset genuinely wants a one-shot intro).

Bar snapping here is generation-side only: it fixes the *requested* length to a
whole number of bars. Trimming exactly on the downbeat and crossfading the seam
belong to the post stage - see the `loop-and-postprocess` skill. Do not tell the
user the loop is seamless because the bar count is right; it is seamless once
`post_process.py` has cut it and the wrap has been listened to.

The snapped length is also a target, not a guarantee. ACE-Step renders on a
25 Hz latent grid, so the decoder rounds the request down to a whole 40 ms
frame: a 30.857 s target comes back as 30.80 s, 57 ms short. Allow **+/-80 ms
(two latent frames)** when comparing - one frame for the rounding itself, one
for the decoder's own edge handling. Measure the real file with `ffprobe` and
treat `barSnappedDurationSeconds` as what the post stage should trim or pad
toward, not as what is already on disk.

### Trailing Silence

The LM planner decides when the song is finished, and it regularly finishes
early: it writes an ending a few bars before the requested length and the
renderer fills the rest with silence. The first real chiptune test asked for 18
bars and got content up to bar 15 followed by 5.05 s of nothing. In a game that
is not a short track, it is a track with an audible hole every time the loop
wraps.

Every candidate is therefore measured (50 ms RMS windows, -45 dBFS threshold)
and the numbers are recorded as `leadingSilenceSeconds` and
`trailingSilenceSeconds` in the candidate params, plus printed in the run
summary.

For looping assets the driver also records `params.loopViable`, which is false
when either end carries more than 0.75 s of dead air:

- **Auto mode** retries with a fresh seed until a take is loop-viable, up to 3
  candidates per invocation. Rejected takes stay on disk and in the manifest -
  one of them may still be the best available. If none qualify, the run still
  finishes `done` and prints a warning naming the closest candidate and its
  figures. Passing `--candidates N` explicitly turns the retry off: an explicit
  count is an instruction, not a starting point.
- **Manual mode** never retries. It annotates and prints the figures so the
  person choosing sees them first.
- **Non-loop assets** get the measurements, no flag and no policy.

When nothing is loop-viable, the fix is the requirement, not another roll of the
dice: shorten `requirement.durationSeconds` toward where the music actually
stops. **A loop does not have to be the requested bar count to be valid** - the
post stage trims to the last contentful bar boundary, so a 15-bar loop out of an
18-bar request is a good outcome, not a failure. On the measured chiptune take
that is exactly what happens: 4.10 s of trailing silence becomes a bar-exact
25.714 s loop.

Set expectations accordingly: on the chiptune case the loop prompt hints cut the
trailing silence from 5.05 s to 3.05-4.10 s across three seeds, but never below
the 0.75 s limit. Prompting reduces the problem; it does not remove it, and no
number of retries will make a planner fill bars it has decided to end before.

If `loop` is set but BPM or time signature is missing, the backend logs a
warning and generates the raw duration. Set both.

## Vocal Songs

Instrumental is the default everywhere. `requirement.vocals` is false out of the
box, and ACE-Step then sends its `[Instrumental]` marker.

For a song with words:

```bash
python3 "<plugin-root>/scripts/init_asset.py" ending-song --type bgm \
  --prompt "Genre: wistful indie folk ending theme. Key: G major. Vocals: soft female lead, close and breathy. Arrangement: fingerpicked guitar and soft piano; brushed drums enter in the chorus." \
  --duration 90 --bpm 96 --no-loop --vocals --lyrics "[verse]
Morning light along the harbour wall
[chorus]
We carry the light home"

python3 "<plugin-root>/scripts/backends/generate_minimax.py" ending-song
```

Rules that hold for both music backends:

- `requirement.vocals` true with `requirement.lyrics` empty is a `user_error`.
  Wordless singing reads as a broken backend, so it is refused rather than
  generated. Write the lyrics, or set `vocals` to false.
- `requirement.lyrics` set while `vocals` is false is ignored by ACE-Step, with a
  warning; MiniMax refuses the run outright.
- The language is detected from the lyrics themselves; both models sing many
  languages. ACE-Step caps lyrics at 4096 characters. MiniMax caps the caption
  and lyrics **together** at 5000 tokens; its worker tokenizes the real prompt
  before loading any weights, so an over-long one is a `user_error` in seconds
  rather than after the model has loaded, and the message gives the actual token
  count and how far over it is.

### Lyrics Format

Section tags drive the arrangement. Write each tag on **its own line**, in
lowercase square brackets, with the sung words on the lines below it:

```
[verse]
Morning light along the harbour wall
Every quiet street is yours and mine
[chorus]
We carry the light home
```

MiniMax-Music3 drops any text that shares a line with a leading tag - that is its
input contract, not a bug - so `[verse] Morning light` loses the whole line.
Usual tags: `[intro]`, `[verse]`, `[pre-chorus]`, `[chorus]`, `[bridge]`,
`[outro]`. The tags are also the structure lever: this model has no separate
structure control, so the shape of the song is the shape of the lyrics.

### Caption Structure (MiniMax-Music3)

`requirement.prompt` is the model's only channel for everything that is not sung.
Write it in three parts, in this order:

1. **Global metadata** - genre, BPM, key, mood and how the mood evolves.
2. **Vocal details** - gender, timbre, delivery, harmonies, effects.
3. **Arrangement** - instruments, what enters when, production texture.

> Genre: acoustic pop. BPM: 96. Key: C major. Warm and intimate, building gently
> into the chorus. Vocals: soft female lead, close and breathy, light stacked
> harmonies in the chorus. Arrangement: fingerpicked guitar and soft piano;
> brushed drums and upright bass enter in the chorus.

`requirement.styleTags` are appended to the caption as usual. When
`requirement.bpm` is set and the caption does not mention BPM, the driver appends
`BPM: <n>.` - a caption is the only place this model can read a tempo. It is
documented not to honour tempo, key or instrumentation exactly, so **measure the
result rather than assuming it obeyed**.

### Which Backend For A Vocal Track

| Situation | Backend |
| --- | --- |
| Exploring melodies, testing several lyric drafts, iterating on style | `generate_acestep.py` - tens of seconds per candidate, 48 kHz, and it takes reference audio. |
| The take that ships, where the singing itself carries the scene | `generate_minimax.py` - clearly stronger vocals, at minutes-per-candidate and the license notice above. |
| A vocal track that must loop | `generate_acestep.py`. Songs with verses and a chorus rarely loop well from either model, and only ACE-Step gives structured tempo control to snap against. |

A sensible workflow is both: settle the lyrics and the style on ACE-Step, then
re-render the approved idea once on MiniMax. Candidates append rather than
overwrite, so both takes can live in the same asset - the `backend` field on each
candidate records which produced it.

## Reference Audio (ACE-Step only)

Set `requirement.referenceAudio` to an absolute or workspace-relative path to
condition generation on the style of an existing track. Text prompt and
reference can be combined; either one alone is enough to run.

`requirement.referenceStrength` is how strongly the reference should survive, so
**higher means closer to the reference**. It maps straight onto ACE-Step's
`audio_cover_strength` with no inversion.

| Value | Result |
| --- | --- |
| `1.0` | Full style conditioning on the reference. |
| `0.7` | Default. Clearly related, still led by the prompt. |
| `0.2` | Light style transfer; the prompt dominates. |

The backend samples 30 seconds from the reference as three 10 second segments
taken from its front, middle and end; nothing else in the file is used. This is
style conditioning, not cover mode: it borrows character, not melody. Cover,
repaint and audio-to-audio are not wired up yet.

## Duration

ACE-Step 1.5 is trained for 10-600 s and hits the requested length closely.
Anything outside that range is a `user_error`; under 10 s the asset is a sound
effect, so use `generate_sa3.py` instead.

Practical limits on a 12 GB card with the LM planner loaded: around 8 minutes
per track. A long track also costs proportionally more time per candidate, so
explore the idea at 30-60 s before committing to a 5 minute render. For scale, a
31 s instrumental on a 12 GB card takes about 17 s of generation once the models
are loaded; loading them costs another minute or two on every run.

MiniMax-Music3 generates 10-360 s (9000 frames at 25 fps - its README says five
minutes, its code allows six). `requirement.durationSeconds` is a **ceiling**
there, not a target: the language model emits an end token when it decides the
song is over, and the driver warns when a take lands more than 10% short. Longer
lyrics are what buy a longer song.

### MiniMax-Music3 Cost

Set expectations before starting a run:

- The first run downloads the diffusers components into the Hugging Face cache -
  **27 GB measured**, and nothing lands in the game workspace. On a 25 MB/s link
  that is about half an hour of pure download before any audio exists. Set
  `HF_HOME` to a roomier drive first if the default cache drive is tight;
  `doctor.py` warns when space is short.
- Generation is autoregressive - the 8B language model emits 25 frames of audio
  per second of music, one at a time - and on a 12 GB card the model has to be
  streamed leaf by leaf from system RAM to fit. **Measured on an RTX 4070 Ti
  (12 GB): 75 seconds of music took 36 minutes**, roughly 29x real time, with the
  model already cached (loading it costs about 25 s more). Cost scales with the
  requested length, so a 5 minute track is a multi-hour render. The worker
  timeout is 90 minutes plus 60 minutes per candidate for exactly this reason; a
  `timeout` on the first run is usually the download, and re-running resumes it.
- VRAM is not the limit, time is: peak torch allocation on that run was 5.7 GB,
  and the autoregressive KV cache grows with the song's length (it added about
  0.8 GB over 75 seconds). Cards with 22 GB or more skip the leaf-level streaming
  automatically and run several times faster. There is no flag: the worker reads
  the card.

Because of that cost, quote the wait to the user before launching a MiniMax run,
and prefer one candidate at a time.

## Candidates And Seeds

- Manual mode defaults to 3 candidates, auto mode to 1.
- Candidates are generated one at a time to keep peak VRAM at a single track's
  worth. Each gets its own seed; pass `--seed N` to make a batch reproducible
  (candidate N uses `seed + N - 1`).
- Re-running appends (`cand-04.wav`, `cand-05.wav`, ...) instead of overwriting
  earlier takes, so nothing is lost by trying again. Candidates from different
  backends can share one asset; each records its own `backend`.
- **MiniMax-Music3 never auto-retries.** ACE-Step's loop-silence retry (below)
  is deliberately off there: a retry would cost another multi-minute render, and
  spending that unattended is not the driver's call. The silence measurements and
  the `loopViable` annotation are still recorded - they are just yours to act on.

## Dry Run

Set `AUDIO_PIPELINE_DRY_RUN=1` to exercise the whole flow without a GPU or the
generation environments. ffmpeg synthesizes a stereo tone per candidate at the
bar-snapped duration - 48 kHz for ACE-Step, 44.1 kHz for MiniMax, matching what
each really renders - and the manifest is filled in as usual, with
`dryRun: true` in the candidate params. Use it to check wiring and bar snapping,
never to judge audio.

## When It Fails

The backend records a `stages.generate.failureKind` and prints an actionable
message. Do not retry blindly; fix the named cause first.

| failureKind | What to do |
| --- | --- |
| `user_error` | Wrong asset type, missing prompt, missing reference file, duration outside the backend's range, vocals without lyrics, an over-long prompt, missing ffmpeg, or a missing generation environment. On MiniMax also: `vocals: false`, `referenceAudio` set, or no CUDA device. The message names which. |
| `oom` | Shorten the duration, close other GPU work, or generate fewer candidates per run. |
| `model_download_failed` | The weights could not be fetched. Check the network and the free space on the drive holding `~/.claude/audio-pipeline/acestep/checkpoints` (ACE-Step) or the Hugging Face cache (MiniMax, 27 GB). |
| `backend_error` | Read the message; it carries the worker's own error. |
| `timeout` | ACE-Step: the run exceeded 90 minutes. MiniMax: 90 minutes plus 60 per candidate. Almost always a first-run weight download that is slower than the budget. Check that the cache grew, then re-run: the download resumes. |

## Verification Checklist

Before declaring the generate stage done, confirm all of the following:

- `stages.generate.status` is `done` and `stages.generate.backend` is the backend
  that was actually used (`acestep` or `minimax`).
- Every entry in `stages.generate.candidates` has a `file` like
  `generate/cand-01.wav` that exists on disk and is non-empty.
- Each candidate records the seed that produced it.
- The files are stereo at the backend's own rate - **48 kHz for ACE-Step,
  44.1 kHz for MiniMax-Music3** (`ffprobe` is enough here). For ACE-Step the
  duration matches the request within +/-80 ms, two 40 ms latent frames; for a
  looping asset compare against `barSnappedDurationSeconds`, not the original
  request. For MiniMax the duration is a ceiling, so a shorter file is normal -
  check it is not *much* shorter than the lyrics justify.
- For a looping asset, every kept candidate has `params.loopViable` true, or the
  shortfall has been discussed with the user rather than passed off as fine.
- For a looping asset, the track does not fade out and does not open with a
  one-shot intro flourish.
- Vocal tracks sing the supplied lyrics; instrumental tracks have no voice.
- For any MiniMax candidate: the user has been told about the
  "MiniMax-Music3" UI-attribution requirement, and `params.licenseNotice` is
  present on the candidate.
- `stages.generate.failureKind` is `null`.

ACE-Step candidates come out peak-normalized to -1 dBFS (its own default), so a
peak reading of exactly -1.0 dB is expected and is not the same thing as the
`requirement.targetLufs` the post stage will apply. MiniMax candidates are only
clamped to [-1, 1] and are not normalized, so a sample peak of exactly 1.0 and a
**true peak slightly above 0 dBFS** are both normal there (the measured test run
came out at -14.8 LUFS integrated, +0.11 dBTP). Loudness is the post stage's job
either way; do not treat an over-0 true peak as a broken candidate.

Every backend writes 32-bit float WAV (`pcm_f32le`) - that is what `torchaudio`
produces from a float tensor. The post stage decides the shipped bit depth.

If any item fails, fix it and re-verify before moving to the post stage.

## Next Stage

After selecting a candidate, run the post stage - see the `loop-and-postprocess`
skill. It is where a loop actually becomes a loop: the take is trimmed to its
last contentful bar, the seam is equal-power crossfaded and measured, the track
is normalized to `requirement.targetLufs` (-16 LUFS for music) under a -1.0 dBTP
ceiling, and the WAV/OGG exports are written.

```bash
python3 "<plugin-root>/scripts/post_process.py" <slug> --candidate generate/cand-03.wav
```

Bar snapping only works there for ACE-Step candidates, which record the tempo
they rendered to. A MiniMax take needs `--bpm <measured tempo>` or it falls back
to a content-boundary cut.
